# 语海Voc

从七鱼支持会话整理商家使用知汇鸽时的高频问题、配置指导、排障方法和有出处的缺陷记录。前端使用 React、TypeScript 和 shadcn/ui；原独立登录及会话接收服务继续使用。

## 目录

- `frontend/`：React + Vite + Tailwind CSS 前端。使用真实 Radix 控件、Recharts 图表与 Lucide 图标。
- `console/`：现有 Python 看板服务，对应服务器 `/opt/qiyu-console`。
- `receiver/`：现有 Python 消息接收服务，对应 `/opt/qiyu-receiver`。两个代码副本包含各自的兼容修正，不能互相整包覆盖。
- `console/src/web/static/`：前端生产构建结果，由现有 Python 服务提供。

## 开发

```sh
cd frontend
npm ci
npm run dev
```

前端生产使用同域 `/api/*` 接口。开发时可通过 Vite 代理连接本机看板服务；不在源码中保存管理员密钥、Cookie 或服务器环境文件。

```sh
npm run build
```

前端数据刷新回归运行 `npm test`。VOC 工作台在任务运行时每次请求结束后等待 5 秒更新结果，空闲时每 30 秒检查新任务；隐藏标签页暂停轮询。相同筛选范围的后台更新保留已有内容，切换范围立即隐藏旧数据，已打开的证据详情不随进度反复重载。

页面切换使用 React 过渡；首次读取、筛选、分页和详情使用灰阶骨架，提交、清洗及文件下载共用顶部细线进度。快速请求不会被动画延迟，同范围后台复查不触发顶部加载条。并发请求独立计数，失败或取消后释放加载状态；显示设置关闭切换动画、或系统启用减少动态效果时，加载提示保持静态。

## 登录与数据

登录保留原有独立 `/login` 页面、管理员密钥和 `qy_admin` Cookie。前端遇到 401 跳回原登录页，不引入新的鉴权服务。

页面只读取业务库，已移除演示数据入口，旧的演示来源请求也会被拒绝。问答列表由服务端搜索和分页，详情使用真实脱敏上下文。未发现回复只表示抽取答案为空，不表示问题已确认未解决。

导入沿用原接口的文件预览、摘要核验、事务确认与同源校验；重新清洗需要明确确认。仓库不包含生产数据、环境文件或密钥。

## VOC 新整理

完整业务定义、处理流程、自动入库条件、统计口径和验收边界见 [VOC 分析算法规范](console/docs/voc-algorithm.md)。

`/#voc-chat` 是独立的“问问数据”聊天页，可从侧栏、使用支持页进入，也可带当前筛选在新标签中打开。最近 20 个对话与草稿保存在当前标签页的 `sessionStorage`；不是跨设备历史。每个对话固定自己的查询范围，历史回答的引用保留实际日期与条件。支持新建、切换、复制、停止等待和删除本窗口对话；查询失败会恢复问题。聊天仍使用现有的只读 `/api/voc2/assistant`，不增加模型网关或新的鉴权流程。

`/#voc-next` 提供新的增量清洗工作台，使用独立派生库，不覆盖原问答、旧 VOC 或人工维护内容。处理链路为：来源与身份核验 → BGE 中文语义检索 → 通用模型拆分咨询意图和提取原文依据 → LangExtract 精确定位 → Python 质量门控与去重计数 → 可复用知识/高频问题/异常缺口。

业务域通过 `VOC_DOMAIN=zhihuige` 启用，与模型渠道独立。七鱼是数据来源，咨询主体是商家，内容围绕知汇鸽与电商平台的实际配合使用：

- **场景配置与使用指导**：配置目标、触发条件、操作路径和适用范围。
- **功能异常与排障**：商家报告的预期与实际表现，分别保留待定位、配置原因、平台限制和已确认缺陷。未触发、反馈技术或推测不能自动升级为已确认 Bug。

SKU、规格、价格及转述的买家问法属于复现背景，不能直接沉淀为买家商品政策。同一现象先统计为需求主题，再按原因、条件及操作方法生成多个知识分支；未完成排查的片段不阻断其他有完整依据的方法。知识包括功能说明、配置指导、排查建议和已验证的临时处理方法；有依据的软件能力与限制事实无需编造操作步骤。符合门控的知识自动可用，效果是否已验证另行记录。只有明确确认过的缺陷进入缺陷清单，不能把它当作已修复。

高频主计数按会话、访客和主题去重；补 SKU、截图和追问保留为咨询片段。知识分支独立保留版本及来源，包含商家报告、客服诊断和效果验证的角色与原句跨度。来源不全、真正冲突及不合格模型输出有明确记录；不会要求全部结果重新人工审批。

来源核验与操作效果分开判断。`conversation_verification` 保留完整七鱼会话、人工消息锚点和客户反馈的核验结果。`knowledge_reuse` 决定条目在知识库的用途。有原句和完整条件的低风险配置步骤及只读排查指引可自动展示。已验证处理方法需要客户明确执行对应步骤并确认效果。其他有来源的内容保留在来源记录中，系统在会话更新后重新判断。

模型仅负责结构化提取与判断，不负责生成统计数字或无来源业务口径。模型 ID 不参与业务分支；千问只是测试渠道之一，其他 OpenAI 兼容网关可沿用同一合同，原生协议可实现 Provider 适配器。每次请求仅携带当前来源和最多五个候选主题。答案必须保留条件、数字与否定，来源变化会使已有知识失效；资料收集、个案回复和冲突单独进入异常，符合门控的知识自动进入可用列表。

必要阻塞缺口必须引用当前请求及原文依据；未被询问的扩展建议单独记录，不否决已有事实，也不作为新知识事实。领域任务使用独立输出预算，不能把响应截断当成成功。可重试的模型格式或引用错误最多自动纠错一次，每次尝试都计入调用与用量预算，不使用失败输出作为知识。连续三条来源最终失败时停止本轮，剩余来源保持待处理；网关限流、HTTP 故障和超时采用安全错误信息，日志不包含密钥或上游正文。

“问问数据”对话框通过固定只读工具查询高频问题、覆盖量、客服接待原话和可用知识。统计由 Python 计算，答案附可打开的来源；对话不执行模型生成的 SQL、代码或发布指令。

对话页沿用工作台的灰阶面板和动效，历史、引用来源与查询详情按需展开。追问继承上一轮实际日期和引用，新对话使用页面默认范围。先对具体知识、条件、步骤和会话片段重排，再由已配置的网关模型基于证据组织答复并独立核对。统计数字由程序原样呈现，直接查数无需额外成文；证据不足、模型成文未通过核对或来源发生变化时，显示相应的原文依据或缺口。个案回复不升级为已验证通用答案。

运行环境需安装 `console/requirements-voc.txt`，另行准备 CPU PyTorch 和本地 BGE 模型缓存；服务运行期间不下载模型或执行远程模型代码。完整接口、模型评测命令与门控说明见 [VOC v2 文档](console/docs/voc-v2.md)。

模型任务使用独立的 `qiyu-voc-worker.service`。队列固化启动时的模型配置，网关密钥仅放在短期私有文件中，worker 读取后即删除；网页重启不会中断已在运行的模型任务。每小时增量入口使用 `console/deploy/qiyu-hourly-voc-v2.conf` 覆盖原 hourly service 的执行命令，时间仍由原北京时间整点 timer 控制；无新增数据或已有任务时跳过。

```sh
sudo install -m 644 console/deploy/qiyu-voc-worker.service /etc/systemd/system/
sudo mkdir -p /etc/systemd/system/qiyu-hourly-analysis.service.d
sudo install -m 644 console/deploy/qiyu-hourly-voc-v2.conf /etc/systemd/system/qiyu-hourly-analysis.service.d/voc-v2.conf
sudo systemctl daemon-reload
sudo systemctl enable --now qiyu-voc-worker.service qiyu-hourly-analysis.timer
```

worker 与 Web 服务均需使用已安装依赖的 Python 环境，并通过 `VOC_EMBED_MODEL_PATH` 指向已校验的本地模型。网关设置和原独立鉴权继续复用。领域提取使用 12,000 输出 token 上限，给网关计入的推理用量留出空间；本次部署将模型等待时间设为 180 秒，后续仍可从模型网关设置调整。新链路先在独立入口验收真实数据，默认旧入口在验收前保留；未启用飞书推送。

## 原 VOC 高频问题（兼容入口）

“高频问题”工作台支持用大模型整理客户诉求、标准问法和业务主题，再由管理员复核。原有“问题簇”保留规则聚类，两个入口的数据含义不同。

- 点击“AI 整理”创建后台任务，按当前日期、客户群及客服范围处理尚未完成的问答。模型输入先清理附件元数据并脱敏，模型输出须通过字段和证据 ID 校验。
- 模型建议进入待复核列表。管理员可以编辑问题和归并边界、确认或忽略、合并标准问题，以及将勾选的原句排除或拆成新问题。
- 主题使用独立稳定编号；涉及问答数和客户数由真实证据集合计算。一个问答可以涉及多个诉求，各主题数量不能直接相加当作总问答数。
- 人工修订保留，新增证据单独待核对。处理记录按输入内容、模型和提示词版本去重，失败任务可重试；模型失败不写成成功结果。
- 原始会话、问答记录和原有登录鉴权保留。VOC 不会自动发布知识库或向客户发送内容；人工新增标准问题在没有关联证据时次数为零。

“知识沉淀”将标准问题与客服实际回复一起整理为候选问答。每条候选包含适用条件、日常回复范式、原句依据、冲突说法和缺失信息，供管理员编辑和确认；已确认内容可以导出。模型不能把未回复的问题补成业务承诺，也不能把不同产品或不同条件下的回复直接混成通用答案。重新生成保留为新的候选版本，不覆盖人工确认的知识。

当前范围或标准问题没有有效客服回复时，界面显示来源覆盖提示，后端拒绝创建知识任务，不调用模型。应先补采客服侧消息，或导入包含明确客户问题、客服回答的完整记录。访客方向、机器人或联调样例不能靠猜测充当真实客服回复。

### 原小时任务（未安装 v2 覆盖配置时）

`console/deploy/qiyu-hourly-analysis.timer` 按北京时间每个整点启动增量整理，使用看板服务已有的模型配置。每轮先处理最多 100 条新增或有变更的问答，再为最多 10 个有有效客服回复的主题生成待审核知识草稿。问答内容、模型及提示词版本均未变化时不重复分析；相同来源的知识草稿、已确认或已忽略记录也不重复生成。

任一手动或自动模型任务仍在运行时，本轮跳过，不中断任务或重复启动。一次任务超过一小时也不会并行执行下一轮。没有待处理内容时不调用模型；新证据生成新的知识草稿，不覆盖人工修订，也不会自动确认或发布知识。会话消息同步仍每分钟检查，与模型整理分别调度。

```sh
sudo install -m 644 console/deploy/qiyu-hourly-analysis.service /etc/systemd/system/
sudo install -m 644 console/deploy/qiyu-hourly-analysis.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now qiyu-hourly-analysis.timer
systemctl list-timers qiyu-hourly-analysis.timer
```

在服务器 `/opt/qiyu-console` 目录运行 `python3 -m src.hourly_analysis --check` 可只读检查待处理内容，不创建任务或调用模型。自动任务在独立进程运行，不需重启看板或消息接收服务；运行记录可用 `journalctl -u qiyu-hourly-analysis.service` 查看。

### 模型网关设置

管理员可从侧栏“系统设置 → 模型网关”修改公共 HTTPS 网关的 OpenAI 兼容接口基础地址、API Key 和模型 ID，并读取模型列表验证连接。模型列表不是必需条件，不支持该接口的网关仍可手动填写模型 ID。保存后，后续 VOC、知识草稿和每小时自动任务使用新配置；已经启动的任务保留启动时的配置。

现有密钥只显示是否已配置，不返回浏览器。地址不变时，密钥留空表示保留；更换地址必须重新填写密钥，避免将原密钥发送给新地址。设置沿用原管理员 Cookie 与同源写保护，配置只保存在服务端，不放入浏览器存储或仓库。

也可以直接修改看板服务的环境文件；手动修改后需重启看板服务，使网页发起的任务加载配置：

```dotenv
LLM_BASE_URL=https://your-gateway.example/v1
LLM_API_KEY=your-server-only-key
LLM_MODEL_MAIN=your-model-id
LLM_DRY_RUN=0
LLM_BATCH_SIZE=4
LLM_CONCURRENCY=1
LLM_TIMEOUT=120
```

密钥仅通过管理员设置接口提交，不通过查询接口返回，不放入前端构建、仓库及任务日志。开发测试使用隔离数据，禁止真实模型调用。`/api/voc/*` 沿用原管理员 Cookie 和同源写保护。

支持 `thinking` 参数的网关可设置 `LLM_THINKING=disabled`，减少结构化整理的思考耗时及输出截断；默认留空，不向其它网关发送此参数。模型输出不完整、JSON 或证据校验失败时任务保留明确错误，重试只处理未成功的问答。

## 接收客服回复

接收端已持久化且通过验签的 `DATA_ONLINE_SESSION_END` 事件，可由独立进程按其真实 `id` 查询官方单会话详情和消息接口，回补完整会话。推送请求中不等待外部接口，也不修改原接收鉴权或握手。

```sh
cd /opt/qiyu-receiver
python3 -m src.push_sync --limit 20
```

`receiver/deploy/qiyu-message-sync.service` 与同名 timer 提供后台同步，每次任务结束后一分钟再检查。会话按事件版本去重，失败退避重试；只重抽本次会话的问答，不全库重聚类或改写其它问答。来源响应不完整、身份不明或不能安全匹配旧原文时会保留错误并拒绝覆盖。

人工客服文本须有明确 `from=0` 与正数 `staffId`；访客、机器人和未知身份分别处理。完整来源消息字段保留在同步台账，原始明细归档时同步清除，不重新拉回已过保留期的正文。测试相关词只作为核对提示，不能仅凭关键词判定业务真伪；已知联调样例不能冒充已确认的业务知识。

消息级发送人身份与会话级访客 ID 不直接混用；多访客依来源身份分段，身份控制行只供抽取使用，不进入网页正文或模型输入。重新清洗仍复用相同分段和客户身份。

## 更新服务

1. 备份当前 `/opt/qiyu-console` 与 SQLite 一致性快照。
2. 执行前端 TypeScript 检查、生产构建与现有后端测试。
3. 将前端 `dist/` 放入新的静态资源目录，原子切换到 `console/src/web/static/`。
4. 保留上一版目录用于回退，核验登录页、API、静态资源与接收服务健康状态。

仅静态前端更新时无需重启消息接收端，不变更原鉴权、Caddy 路由或数据库结构。
